# Fixed Add and ReLU ASIC cores

Run `python3 scripts/asic/fixed.py`. The bench instantiates two physical `AsicFixed` cores: `OP=1` for wrapping INT32 Add and `OP=0` for signed ReLU. Each has its own 64 KiB synchronous RAM. Function selection happens at elaboration; runtime `operation`, `fused`, `unit` and phase fields cannot turn Add into AddReLU or combine the cores.

The host interface uses a pipelined memory with variable read response latency. It accepts one host write per cycle while idle; `write_pending` remains high until all accepted writes commit. The caller must wait for it to clear before a new read or start. A simultaneous read/write request returns the old word. Jobs latch `count`, source word addresses and destination on start. Counts are positive and all accessed regions must fit the 16384-word capacity. Exact in-place operation is supported; arbitrary partially overlapping arrays are outside the contract. `busy` covers execution and final write drain, and `done` pulses only after the final write commits.

`AsicFixedMemory` contains 128 banks of 128 words. Registered request addresses feed registered bank decoding, synchronous bank reads, an eight-bank registered selection stage, and a registered final output. A read accepted at edge 0 produces `rvalid` after edge 4; a write accepted at edge 0 commits at edge 3. The write pipeline trails reads to preserve simultaneous-request read-first behavior. Add uses a two-stage arithmetic path: parallel eight-bit sums for both carry inputs, followed by registered carry selection. It issues one element every two cycles; ReLU issues one each cycle. Execution takes `2*N+12` cycles for Add and `N+11` for ReLU in this fixture, including pipeline fill and final write drain.

Use `python3 scripts/asic/fixed.py --sram --output build/experiments/asic/retimed/fixed-sram` to run the same pipeline with the `ASIC_SRAM` macro interface. The functional macro model samples chip selects on the falling edge and accesses data on the rising edge; it poisons simultaneous same-address physical read/write collisions. This verifies the source pipeline against the macro interface, but does not establish physical timing closure. Synthesis must use the same `ASIC_SRAM` definition and the actual SRAM library.

The test checks signed wrapping, negative results, two different input streams, lengths 1/3/7/8/31/128/1024, exact in-place jobs and the final RAM word. Add output is checked before it is copied to ReLU memory, so an accidental fused operation cannot pass by producing only the final activation. A sentinel also verifies that Add does not change the other core's memory. Runtime descriptors are changed after launch to check capture.

Reports separate core execution cycles from the actual testbench read/write copy, including the final destination write drain. A count-N chain has N words read from Add and N words written to ReLU. These are fixture-port bytes, not measured TileLink or DRAM traffic; this bench alone establishes neither whole-SoC performance nor a CGRA speedup. Full adapter/DMA tests remain necessary.
