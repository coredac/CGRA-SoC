## Configuration sources

The single-CGRA configuration is layered:

- `configs/arch/arch.yaml` owns CGRA structure and functional-unit choices.
- `configs/soc/cgra_soc.yaml` owns the SoC interface and memory settings.
- `configs/soc/autolink/gc.yaml` owns the two-IP CGRA and Gemmini SoC settings and automatic task.
- `configs/soc/autolink/gci.yaml` selects packed INT8 input for the two-IP automatic task.
- `configs/soc/autolink/gca.yaml` owns the three-IP CGRA, Gemmini, and AES SoC settings and automatic tasks.
- `configs/soc/autolink/gca_short.yaml` owns the shorter Gemmini → CGRA → AES automatic graph.
- `configs/soc/autolink/gcp.yaml` owns the Gemmini, CGRA, and Pool settings.
- `configs/soc/autolink/res.yaml` owns the residual block settings and automatic graph.
- `configs/soc/autolink/tiles.yaml` owns the native Conv → ReLU → Pool tiled graph and two buffer regions per buffered IP.
- `configs/soc/autolink/res_tiles.yaml` owns the native tiled residual graph with preloaded skip tiles.
- `configs/soc/autolink/multi.yaml` owns the five-instance Gemmini/CGRA/Pool access demo.
- `configs/soc/autolink/block.yaml` owns the four-instance projected residual tile graph and 64 KiB CGRA memories.
- `configs/soc/autolink/blocks.yaml` uses the same graph with 128 KiB Gemmini SPMs and INT8 windows on both CGRAs for sequential projected residual blocks.
- `configs/soc/autolink/resnet.yaml` adds a CPU-controlled Pool and gives each CGRA 128 KiB for the synthetic ResNet-8 chain; its AutoLink graph remains the projected-block graph.
- `configs/soc/autolink/graph.yaml` fixes the five-IP hardware and graph capacities for runtime graph replacement; `configs/graphs/` contains software-loadable graphs for that system.
- `configs/soc/autolink/attention.yaml` selects two Gemminis and one CGRA for single-head causal Attention; `configs/arch/attention.yaml` gives its three resident Softmax phases 64 control slots.
- `configs/kernels/kernel_*_4x4.yaml` owns kernel metadata and execution counts.

Do not restore the deprecated mixed kernel schema or add fallback reads for its old fields. Keep multi-CGRA architecture and SoC settings in their matching files under `configs/arch/` and `configs/soc/`.

The single-CGRA SoC setting `execution.ctrl_count_bits` selects the native execution-step counter width at generation time. Its default preserves VectorCGRA's 11-bit counter. It does not change control-memory capacity or packet layout. Runtime control-step counts must fit this width; the projected residual configuration uses 14 bits, enough for 16010 ReLU steps from an 8×8×32 core plus halo.

The main generation entry points are:

- `scripts/generate_single_cgra.py`
- `scripts/generate_multi_cgra.py`
- `scripts/cgra_fast_api.py`
- `scripts/generate_auto_links.py`
- `scripts/generate_accels.py`
- `scripts/generate_cgra_link_control.py`
- `scripts/generate_gemmini_ext_spm.py`
- `scripts/generate_cgra_spm_window.py`
- `scripts/openfpga/generate.py`

Use the scripts' `--help` output and the current YAML schema instead of copying arguments from old plans or logs.

## Supported systems

### CGRA

Single-CGRA fast APIs support FIR, ReLU, Add+ReLU, GEMV, Histogram, and AXPY. GEMM and SAD are unsupported. Track kernel bugs and validation limitations in GitHub Issues rather than recording them here.

Softmax has three sequential fast-API kernels (`softmax_max`, `softmax_exp`, `softmax_norm`) for ten INT32 logits at scale `1/256`, producing INT32 Q15 probabilities. Their YAML bindings own the SPM layout and are exported as `<KERNEL>_<ARG>` constants; execution counts remain in kernel metadata. Input max-minus-min must fit signed INT32. The polynomial approximation is checked against floating Softmax with a tolerance of 96 Q15 units, and RTL results must exactly match the integer reference. Per-element rounding does not guarantee the probabilities sum to exactly 32768.

Attention uses separate multirow `attention_max`, `attention_exp` and `attention_norm` kernels, preserving the ResNet Softmax interface. Q/K use scale `1/8` and head dimension 64, so raw QK scores have Softmax scale `1/512`; exponential approximation operates on `(max - score) >> 1` as a nonnegative Q8 difference. Causal masking excludes columns above the global query row from max and sum and writes zero probabilities there. Normalization rounds to nearest in the range 0–127, without requiring an exact row sum of 127. Kernel metadata binds row origin, column count, element count and scratch addresses. The three phases use II 12/18/13 at control bases 0/16/40; the final range ends at slot 52 within the 64-slot control memory. Attention's 16-bit execution counter covers the default tile's maximum 36864-step phase.

The initial Attention software supports head dimension 64, sequence lengths divisible by 64 and one native GEMM row block per query tile (at most 16 rows). Q is preloaded in padded native tile blocks, while K and V are reused across tiles. Native working storage, publication slots and retained final output must be disjoint and fit each 128 KiB SPM. The default N=128/tileRows=16 fits; N=128/tileRows=1 does not fit the padded Q allocation. This software layout constraint is not a new RTL tensor-shape restriction.

The hybrid multi-head test uses the same Attention hardware and three resident Softmax kernels. Its generated data selects the head count and hidden width (`heads * 64`); the initial cases have two or twelve heads, N=128 and 16 query rows per tile. CPU-issued Gemmini projections produce INT8 Q/K/V in native blocked SPM storage, with INT32 bias and accumulation. Each head runs the automatic three-stage pipeline to completion before projections overwrite the workspace for the next head. PV saturates its accumulator output to INT8 and writes the head's columns directly into a row-major DRAM concatenation buffer; the final native Gemmini projection consumes that buffer and writes INT8 output to DRAM. Weight and input tiles use existing DMA, and local projection writeback uses `mvout_spad`. The CPU does not copy intermediate payloads or compute model arithmetic. Native load/store and execute configuration must be restored after projections before automatic replay. The host reference applies the same saturation after Q/K/V, PV and output projection and retains the existing causal integer Softmax rule; this does not establish trained-model accuracy.

The synthetic GPT-2 block uses the same two Gemminis, one CGRA and Attention configuration. Manual mode has the CPU issue each attention tile's QK, score DMA, three Softmax phases and PV, waiting for completion between steps. Hybrid mode retains automatic execution inside each head; both modes sequence large phases and heads on the CPU. They share native QK/PV commands, tensor layouts and numerical rules. Both restore the three resident Softmax programs after block kernels overwrite control memory. Its pre-norm path is `U = X + Attention(LN1(X))`, `Y = U + Linear2(GELU(Linear1(LN2(U))))`, including Q/K/V and output projections. Stage tensors are signed INT8 Q4, except Q/K/V and concatenated head outputs, which use Q3. Weights use Q7; gamma/beta use Q6; biases use the matching INT32 accumulator scale. Q/K/V, output projection, Linear1 and Linear2 requantize by divisors 256, 64, 128 and 128 respectively. Softmax retains the existing causal probability codes 0..127; this block divides PV's INT32 result by 127 before saturating, unlike the older MHA fixture. Signed requantization rounds nearest with ties away from zero, then saturates to [-128,127]. Both residual branches use Q4 and saturate only after INT32 addition. Existing Attention/MHA fixtures retain their original numerical rules.

Experimental HeadAuto mode (`2`) automates only the Attention head loop; Manual (`0`) and Hybrid (`1`) retain their meanings. It captures Q/K loads on Gemmini0 and V loads on Gemmini1 as job 1, preserving scores/PV as job 0 and the three CGRA Softmax jobs. The runtime-loaded `configs/graphs/block_load.yaml` graph roots both load stages at `input_ready`, allowing independent execution. Run profile 0 holds this load graph; profile 1 holds the existing tiled Attention graph and repeats the two-profile interval across heads. Runtime address patches add the head iteration to the original Q/K/V addresses and to each INT32 PV output address, retaining the tile offset and dense hidden-width stride. Each head produces two load reports followed by three Attention reports; software drains and checks all reports after the sequence finishes. This uses two existing run profiles and five reports per head, without changing hardware, arithmetic or the block SPM layout. Projection and other block phases remain CPU-controlled.

The experimental whole-block Auto path is `tests/cgra-gemmini/gpt2/auto_block.c`, separate from the existing `gpt2.c` modes. It defines two synthetic prefill shapes: N=64, hidden=128, two heads and FF=512; and N=16, hidden=768, twelve heads and FF=3072. Neither includes KV-cache decode or pretrained-model accuracy validation. `configs/soc/autolink/gpt2.yaml` retains the Attention array and data SPM layout, but reserves 32 jobs per endpoint, 192 packets per CGRA job, 32 run profiles and 512 reports. The original shape uses 28 profiles, 378 reports, 27 allocated job IDs per Gemmini and 23 CGRA jobs. The wide shape uses 16 profiles, 624 reports, 15 allocated job IDs per Gemmini and 23 CGRA jobs. CPU preparation loads affine parameters and captures jobs/profiles; one `auto_link_run` then performs input loading, every block phase and final DRAM output without CPU intermediate launches or payload copies. Non-Attention profiles process one tile and drain before repeating. Original-shape projections use separate column-group profiles and iteration patches across row blocks; N=16 projections use one profile each and iterate across 64-column groups. Software drains and checks reports while the run is active because the wide plan exceeds the 512-entry result queue; this is result handling, not CPU scheduling of intermediate work. Final output checking follows completion. Weights, biases and affine parameters remain DRAM inputs. These are explicit shapes without an implicit larger-shape or DRAM-intermediate fallback. The wide path passed two consecutive full-block inputs without accelerator reset, with all 24,576 output values matching and a successful simulator exit.

The operator-level Hybrid experiment is `hybrid_block.c`, separate from the original head-level Hybrid in `gpt2.c`. It uses the same two shapes, kernels, gather/collect commands and SPM layout as whole-block Auto. The CPU captures only the current operator, launches its profiles, and drains/checks every completion report before reusing profile and job IDs. Tile loops and the complete Attention head loop remain automatic. Software limits usage to 8 run profiles, 8 jobs per endpoint and 128 pending reports; it does not rely on cached configurations outside these slots. Each LayerNorm captures a seven-job CGRA chain. Original-shape FC1 retains all eight column profiles for one operator launch, with whole-block peaks of 8 profiles, 8/8/7 Gemmini0/Gemmini1/CGRA jobs and 96 reports. Wide FC1 splits into two 1536-column batches to bound reports at 72 per batch; the wide plan has peaks of 2 profiles, 2/2/7 jobs and 72 reports, with 624 reports in total. All recapture, CPU scheduling, data movement, execution and report handling count toward total cycles. Both shapes target the existing `gpt2.yaml` hardware without changing its physical capacities. The wide path passed both consecutive full-block inputs and all 24,576 output values, with the stated peaks confirmed for each input and a successful simulator exit. Reduced-capacity hardware validation and area measurements remain separate work.

Auto and operator-level Hybrid LayerNorm chain seven jobs over complete rows: sixteen rows per group at hidden=128, and two rows per group at hidden=768. The wide group contains 1536 elements, so the final requantization's II 22 uses 33792 control steps; four wide rows would exceed the 16-bit counter. Input starts at CGRA word 0, output at 4096 and statistics at 6144, with 16-word spacing between statistic arrays. Auto retains both layers' gamma/beta consecutively from word 16384, ending at word 19456 for the wide shape; Hybrid reloads only the current layer's affine parameters. Native CPU-controlled LayerNorm retains its separate sixteen-row batching and per-phase splitting below.

N=16 cached projections use compact native `gemmini_loop_ws` DRAM-address loops with K chunks of at most 768, including when the addresses resolve to retained SPM. Each job loads bias only for the first K chunk, retains INT32 partial sums and publishes the final 16x64 tile through `STORE_SPAD`; native loop output C is NULL, so the loop does not write the final tensor itself. This path assumes Gemmini's accumulator cursor remains at base zero across all loop users, including Attention; C=NULL is not a cursor-reset operation. Explicit A/B working rows fit below the 60 KiB publication boundary, and each chunk's execute configuration orders reuse after the preceding loop unrolls. Iteration patches advance weight, bias and output column addresses while keeping the input row fixed. These command sequences fit the existing 64-command job capacity without changing Gemmini RTL.

Block LayerNorm consumes one complete hidden row (at most 768 INT8-valued words). Its mean is Q6 in input-code units; squared deviations and variance are unsigned Q8, with a uint32 reduction because the 768-element extreme case exceeds INT32_MAX. Standard deviation is `isqrt(16 * variance + 4096)`, Q6; epsilon is one squared input code, or 1/256 in real Q4 units, not the pretrained GPT-2 epsilon. Normalization computes `trunc_zero((64 * x - mean) * gamma / std) + beta` with Q6 gamma/beta, then requantizes by four to Q4. GELU expands its INT8 Q4 input to Q6 in [-512,508], uses the tested polynomial and requantizes its Q6 output by four. These are explicit synthetic approximations; bit-exact integer checks and floating-reference error are separate results.

LayerNorm kernels traverse multiple rows per launch. Index PEs reset each row's reduction, select its statistics and wrap gamma/beta addresses by column. Sum, squared deviations and affine normalization use II 7/9/11 and completion counts 3/4/6 respectively. Mean, variance and square root traverse contiguous statistics arrays with II 9/7/64 and one completion each. Ordered streams preserve reduction and signed-division semantics, and execution waits for every participating PE. They use the existing 4x4 architecture and 64 control slots per PE; Manual and Hybrid share these kernels.

The block's native matrix helper supports dense row-major matrices with rows divisible by 16, columns divisible by 64 and an inner dimension divisible by 64 up to 3072. It computes 16x64 output tiles with K chunks of at most 768, loading bias once and retaining INT32 partial sums across chunks. Final full-width accumulators go to DRAM for CGRA requantization; no intermediate model arithmetic runs on the CPU. The helper reserves 12 KiB input and 48 KiB weight SPM plus 4 KiB accumulator space. Block CGRA phases replace control memory from slot zero between completed executions, using REARM and preserving SPM; reload the three resident Attention phases before automatic attention. LayerNorm batches up to sixteen rows in SPM, with five contiguous arrays for per-row sum, mean, squared deviations, variance and standard deviation. Each phase splits only at row boundaries so that `II * iterations` fits the Attention hardware's 16-bit execution counter; subsequent chunks use `CGRA_REPEAT` before switching phases. A 16x128 batch uses seven launches; a 16x768 batch uses sixteen. Its input/output rows, gamma/beta and statistics occupy at most 26,192 words of the existing 32,768-word SPM. Requantization and residual chunks also reuse their resident kernel until the function returns. The block kernels' schedule source is `VectorCGRA/validation/test/block_kernels.py`, with root-owned binding and execution metadata in `configs/kernels/kernel_block_*_4x4.yaml`.

Block activation uses a two-PE `block_activation` program: GELU streams its Q6 result directly into fixed-divisor-four requantization, retaining both rounding steps and signed INT8 saturation. The separate Q6 `block_gelu` and general `block_requant` programs retain their contracts. The fused program has II 27 and two completions per launch. The runtime uses at most 2048 elements per chunk, with input at SPM word 0 and output at word 2048; its 55,296 control steps fit the 16-bit counter. The first chunk configures the program and subsequent chunks use `CGRA_REPEAT`.

The optional block `spm` storage policy defines the same N=64/hidden=128/two-head/FF=512 and N=16/hidden=768/twelve-head/FF=3072 shapes as Auto; the default `dram` policy retains its separate larger-shape support. `block_project_spm` keeps native GEMM work in each Gemmini's lower 60 KiB and publishes one 16x64 INT32 tile into bytes [61440,65536). CGRA reads that tile, requantizes with the same integer rule, and writes sixteen packed rows using the destination tensor's stride before the publication region is reused. Let `A=N*hidden` bytes. Gemmini0 retains skip/input, normalized, Q/concatenation, K and branch at byte offsets `65536+{0,1,2,3,4}*A`. Gemmini1 retains V at byte 65536 and dense INT32 PV at byte `65536+A`, occupying `4*A` bytes. After all heads and PV requantization complete, the expanded MLP tensor aliases V/PV from byte 65536 for `N*FF` bytes. The original regions are 8 KiB each with 32 KiB PV and expanded tensors. Wide regions are 12 KiB each, with 48 KiB PV and expanded tensors; retained storage ends at 124 KiB, below the N=16 Attention score slots at 126–128 KiB. These regions do not overlap the native workspaces. Manual, head-level Hybrid, Auto and operator-level Hybrid share the lifetime layout. In `gpt2.c`, the initial activation is copied by CGRA DMA into retained skip storage and the final activation is copied back to DRAM; CPU stage checks read SPM directly outside timed intervals, without staging intermediate payloads. Weight, bias and affine-parameter reads remain in DRAM. Wide Manual, whole-block Auto and operator-level Hybrid each passed two consecutive full-block inputs without accelerator reset. Other shapes require an explicit lifetime/tiling contract or more storage, not an implicit fallback.

The synthetic single-layer GCN uses the existing Attention fabric and `gpt2.yaml`, with no hardware changes. Inputs are 64-channel degree one-hot INT8 features and seeded dense INT8 weights in [-8,8]; Gemmini produces 128-channel INT32 projections with zero bias and rows padded to 16. Host preprocessing inserts one self-loop per node and encodes symmetric normalization weights as positive INT32 Q15, rounding nearest. CGRA follows CSR neighbor indices, accumulates signed products and applies ReLU after reduction; final output remains INT32 Q15 without downshift. Graphs have at most 64 nodes. Projected features, CSR indices, edge weights and final outputs occupy disjoint SPM regions; CSR DMA arrays are padded to four words. One fused kernel uses five PEs at II 10: PE4 supplies gather indices to PE0, PE5 supplies reduction indices to PE1, PE0 streams weighted features to PE1, and PE2 applies ReLU and stores final sums. PE1 retains raw accumulator feedback before predicate gating. Nonfinal tokens remain valid but carry a false predicate through activation, suppressing only memory writes; activation control still runs on every token. Each task expects five completions. All modes split each node's 128 channels so `10 * degree * channels <= 65535`, retaining the same static program. CPU code schedules and validates results but performs no model arithmetic. This is a synthetic functional workload, not a trained-model accuracy test.

GCN Auto/Hybrid scheduling defaults to the generated 16/20/32-node fixtures, requiring 16/20/32 aggregation tasks. Software expands CSR row parameters before launch; no hardware CSR scheduler is assumed. Each fixed-address Gemmini projection job computes one 16x64 tile using 21 commands without field patches and writes full INT32 rows to DRAM. Projection profiles reuse the staged root description, changing only the selected job before each later capture. Sequential profiles drain all projection writes before a CGRA profile pulls projection, indices and edge weights through three raw root copies. Every mode loads the same 95-packet static CGRA program once inside each timed inference. Software resolves 17 payload fields before capture, including five execution counters; each cached task contains 58 configuration/launch packets and zero hardware patches. Manual and cached execution share the payload-resolution helper. Auto retains the whole chain and starts it together with projection in one sequencer submission, using at most four Gemmini jobs, 32 CGRA jobs and five profiles. Hybrid retains at most eight CGRA jobs, submits projection and input copies with the first batch, then recaptures those IDs only after each batch drains; later batches retain the same SPM inputs and accumulated outputs. Its second batch captures a control-only profile selecting job0; subsequent batches reuse that profile, with chain length determined by the newly captured endpoint jobs. The current INT8 SPM window cannot expose raw Q15 values, so all modes use CPU-issued raw output DMA after computation drains. Smaller software cache occupancy does not reduce the instantiated hardware without a later configuration change and rebuild.

The optional `gcn_data.py --star-nodes 64` fixture replaces only the star graph and supports original modes -1/0/1/2. It occupies 16,768 SPM words and has 190 edges including self-loops. With II 10, the task splitter produces center chunks of 102/26 channels and 65 tasks in total, requiring three Auto batches of up to 32 jobs or nine Hybrid batches of up to eight jobs. These counts follow the software limits; the recorded large-graph SoC measurement used the earlier II-26 kernel, not the remapped kernel. Both modes capture eight Gemmini jobs and peak at nine run profiles for the first submission; later batches reuse the drained control-only profile0. This does not enlarge hardware caches. Experimental modes 3–6 reject fixtures with more than 32 padded rows because their job, buffer or readiness assumptions do not cover this shape.

GCN's experimental channel pipeline partitions the 128 output channels into two 64-channel, four 32-channel or eight 16-channel tiles, each containing projections for every padded node. One Gemmini job computes a complete tile and is replayed across channels; the existing fixtures need at most 30 commands and 20 field updates. CSR indices and weights are preloaded inside the timed setup. A two-stage AutoLink graph transfers each completed tile from a compact DRAM slot into a CGRA input slot, then executes the cached per-node aggregation chain. Producer and consumer slots are independent; input addresses follow Slot and final output channel offsets follow TileId. Physical slots retain capacity for 32x64 INT32 values even with narrower tiles. Each CGRA job has two address updates and is reused across tiles. Runtime `arg7` selects the input-row stride, 128 for the original modes or the compact tile width, without changing the schedule. The experiment uses one profile, one Gemmini job and one CGRA job per node; it relies on the existing two slots and 32-job cache, not a hardware change. Final Q15 output is checked in full; the temporary projection ring is not a retained full-Z result. The original eight-job Hybrid scheduling policy is unchanged.

GCN's experimental two-input pipeline shares graph topology and weights between the original features and their signed-negative alternate. Each tile represents one full 128-channel inference, not another layer. One Gemmini job projects all padded rows using up to 50 commands and 18 updates; weight transfers remain at most 64 columns each. TileId selects a distinct packed input and final output, while Slot selects a temporary projection buffer. CGRA replays the original node/channel tasks with two address updates per job; II 10 no longer splits the 20-node star's center. Its input slots occupy words [0,8192), CSR indices [8192,8340), weights [8340,8488), and two retained output regions [8488,16680), within the existing 32768-word SPM. Both final outputs are checked against generated references. The serial control runs existing Auto or Manual independently on the same two inputs and checks both Z and Y; the streaming comparison includes changes in projection batching, capture amortization and CSR reuse, not solely overlap. Timed streaming setup includes CPU input packing. Neither experiment changes the instantiated hardware or measures area.

GCN's node-readiness experiment is restricted to the 20-node star fixture. Software classifies the existing node/channel tasks by whether all CSR neighbors are below node16: fifteen early leaf tasks and five late tasks with II 10. Two fixed-address Gemmini jobs each project 16x128 values using 33 commands and zero updates. Profile0 contains two logical Gemmini0 stages and one CGRA0 stage, with three dependencies: root to first projection, first projection to early aggregation by raw copy, and first projection to second projection by control. The last two stages may execute concurrently; both finish before profile1 copies the remaining projection half into retained full-Z SPM and runs the late chain. The matched serial control changes only the second projection's control predecessor to early aggregation. Both schedules submit the same two profiles once, retain the original SPM layout and check all Z/Y values. This is static CSR-derived grouping, not a dynamic hardware readiness scheduler. Both profiles use TileId0; existing OVERLAP excludes same-TileId concurrency, and fabric counters describe only the final profile, so neither is used to quantify this experiment's overlap.

GCN's split layout keeps aggregation and ReLU as two resident kernels: four-PE aggregation at control slots 0–9 writes final signed Q15 sums; the existing runtime ReLU mapping occupies slots 16–20 and runs once in-place over all node outputs. The first task of each Manual inference restores fixed setup with SWITCH, and ReLU also uses SWITCH. Auto/Hybrid append ReLU as the last cached job, counting it within the 32/8-job budget; it can occupy a separate last batch when aggregation fills the previous batch. No intermediate payload reaches DRAM or CPU, and no extra CPU launch separates Auto's aggregation and ReLU when they fit in one batch. All static loads, captures, SPM reads/writes, launches and final output DMA remain timed. The optional fifth `gcn.c` argument selects 0=fused, 1=split or 2=compare; split supports only original modes -1/0/1/2. Default fused and experimental cross-IP modes retain their mappings.

GCN's optional grouped scheduler (modes 8/9, comparison mode 10) uses the unchanged fused kernel on fixtures with at most 32 padded rows. Adjacent tasks share a descriptor only if arguments 0/4/5/6/7 match and CSR/weight/output addresses advance by degree/degree/128 words. The first task is a singleton whose profile performs the three input copies once. Each later group uses a control-only root edge and TileId patches on the three addresses; other fields are resolved before capture. Each group has its own profile with TileId starting at zero, and its endpoint job has no next-job chain. Results arrive once per profile, not once per tile. Auto batches at most 32 group jobs and Hybrid eight; the first batch also reserves run-profile slots for projection within the 32-profile capacity. Subsequent batches recapture job/profile IDs only after the previous run drains, preserving SPM inputs and outputs. Kernel switches and split layouts are excluded. This reduces configuration capture for equal-degree runs but does not reduce node computations or instantiated hardware capacity.

Multi-CGRA tests support homogeneous mesh, 2x2 and 4x4 systolic, scalar FIR, and vector FIR configurations. Their packet headers are fixed, preencoded test inputs. Automatic multi-CGRA control-packet generation is unsupported; do not replace those headers with an ad hoc generator.

The generated fast API is local single-CGRA only. Do not silently extend it to multi-CGRA targets without first defining the packet-encoding contract.

### CGRA + FPGA

The current OpenFPGA integration is a TileLink MMIO fabric flow. It supports AND2, AND2/OR2, bin2bcd, and gcd6 demos with frame-based k4 fabrics. A Chipyard configuration enabling CGRA and OpenFPGA together is not currently supported. Do not describe the existing OpenFPGA-only configs as concurrent CGRA + FPGA systems.

### CGRA + Gemmini

`CGRAMinimalGemminiRocketConfig` combines CGRA and Gemmini. `CGRAMinimalGemminiAESRocketConfig` and `CGRAMinimalGemminiAESAutoLinkRocketConfig` also add AES. These direct-RoCC configurations keep distinct opcodes: CGRA uses `custom0`, AES uses `custom1`, and Gemmini uses `custom3`.

The CPU-mediated Gemmini GEMM to CGRA ReLU demos remain supported. Manual and automatic configurations use the same Gemmini external SPM. `CGRAMinimalGemminiAutoLinkRocketConfig` adds one automatic 128-byte transfer from that SPM to CGRA local SPM. The CGRA DMA reads the Gemmini SPM through TileLink and the system bus; there is no shared staging buffer or intermediate DRAM copy.

The three-IP Manual and Automatic configurations validate one strict sequential pipeline: AES decrypts 256 bytes into the Gemmini shared external SPM, Gemmini runs GEMM with B preloaded by the CPU and publishes 128 bytes at the SPM tail, CGRA pulls the data into its local SPM and runs ReLU, and AES reads the CGRA read-only SPM window and encrypts 128 bytes to DRAM. Manual mode has the CPU start each IP in order. Automatic mode has the CPU preload B, capture the native Gemmini command sequence, and configure the CGRA and both AES jobs; AutoLink uses fixed `aes -> gemmini`, `gemmini -> cgra`, and `cgra -> aes` routes and returns Gemmini, CGRA, and AES destination results. The older Gemmini-to-CGRA and Gemmini-to-CGRA-to-AES demos remain supported.

`CGRAMinimalGemminiPoolRocketConfig` and `CGRAMinimalGemminiPoolAutoLinkRocketConfig` add a `custom2` streaming Pool accelerator. The pipeline runs Gemmini INT8 Conv, CGRA INT32 ReLU, and INT32 MaxPool; Pool element width is selected at elaboration from 8, 16, or 32 bits, while mode, shape, kernel, stride, padding, and addresses are runtime fields. Average mode uses the same DMA and control interface.

`pool_tiles.c` (`CgraPoolTileRocketConfig`, `tiles.yaml`) targets native Gemmini `loop_conv` with 3x3 kernels, packed INT8 transfers, retained CGRA configuration and triple-IP tile overlap. Gemmini accesses its shared SPM through the local DMA path. Focused RTL tests cover packed-input alignment and tails, software-defined command-field updates and Pool row-strided writeback. Tiled `residual_tiles.c` (`CgraResidualTileRocketConfig`, `res_tiles.yaml`) is deferred; its single-Gemmini/single-CGRA reentrant pipeline remains outside the validated scope.

`CGRAMinimalGemminiResidualRocketConfig` and `CGRAMinimalGemminiResidualAutoLinkRocketConfig` validate one residual block with two Gemmini jobs and two CGRA jobs. AutoLink models logical stages with fan-out and a two-input join. CGRA uses `TileWithContextSwitchRTL`; static kernel configurations reside in disjoint native control-memory ranges selected by `execution.ctrl_base` in kernel metadata (default zero). The adapter caches only native per-run initialization and launch packets. Both tests repeat the block without reloading static CGRA configuration; automatic mode also reuses the captured jobs.

AutoLink carries control only. TileLink carries payload data. CPU-rooted graphs snapshot runtime stage-to-endpoint/job bindings, dependencies, physical source addresses, copy lengths, tile geometry, transfer offsets/slot strides and stage regions before a run. Physical IPs, SPMs and table capacities remain fixed at elaboration. Each endpoint executes one computation at a time. Buffered input preparation can overlap execution using a different free SPM slot; streaming endpoints retain watch-before-copy ordering. External producers without a root tile cursor retain coordinated one-round rearming and do not support runtime graph replacement.

`communication.capacity` optionally sets `stages`, `dependencies` and per-endpoint `jobs`; omitted capacities follow the default graph. All declared instances are available to runtime graphs, including instances unused by the default graph. `generate_auto_links.py --graph-yaml` emits a C descriptor against the selected SoC without changing Scala. Both the default and loaded graph must be DAGs rooted at `input_ready`. Software waits for results and graph drain, calls `auto_link_load` with symbolic address bindings, applies any tile/region/transfer overrides, and starts through the existing API. Loading replaces the staging graph and clears unused entries; it does not launch or configure IP jobs. Existing run-cache entries snapshot the whole description, including graph tables. Graph legality, endpoint capabilities and capacities are generator responsibilities, not runtime hardware validators.

### Multiple accelerator instances

`MultiAccelRocketConfig` instantiates the Gemmini, CGRA and Pool instances declared by `communication.instances`. Each entry names an instance and its `type`; stage endpoints refer to that instance name. Same-type SPMs inherit the type's configured size and receive consecutive non-overlapping ranges, unless an entry supplies `base_address`. Control pages follow the highest SPM range, in instance order. The generator emits matching Scala parameters and `accel_t` software descriptors. Address ranges must fit the hardware and remain disjoint.

Multi-instance Gemmini enables the existing native `loop_conv` engine as well as GEMM; this does not change the native instruction interface. `gemmini_capture_conv_at` captures a Conv job through the selected instance's MMIO page and must execute inside that instance's `accel_commands` block. Its execute configuration uses the requested convolution stride. The original helper selects the default Gemmini control page.

Multi-instance Gemmini's native SPM capacity follows the generated instance's `spmBytes`, matching the shared external memory geometry; accumulator capacity remains independently configured.

A named Pool may be CPU-controlled without belonging to the default AutoLink graph. Its RoCC, TileLink and AutoLink interfaces remain available so a runtime graph can select it later.

All members share `RoCCGroup` for CPU commands, with separate SPM, DMA and endpoint connections. `accel_commands(device, { native_calls; })` emits a `custom0/funct127` selection prefix carrying `device.id` in `rs1`; subsequent commands reach that instance unchanged. Prefixes and commands share Rocket's ordered command path. Selecting another target does not wait for IP execution to finish; responses arbitrate independently and preserve their destination registers. These command blocks are single-hart and non-nested, and an interrupt must not change the target during a block. Every native command sequence must select its target; there is no implicit initial target. Native FPU, custom CSR and RoCC DCache access are not provided by this group.

MMIO helpers with an `_at` suffix take the matching descriptor's control base; they do not select a RoCC target. CGRA job configuration includes native packets and therefore belongs inside its target's command block. AutoLink connects the named endpoints directly, independent of CPU selection. The first declared CGRA endpoint collects the entire graph's result stream; other CGRA endpoints expose their own configuration pages without duplicate result queues.

The five-IP demo has two independent single-CGRA copies, two Gemmini instances and one Pool, not a VectorCGRA mesh. Both tests use `gemmini0 → cgra0 → gemmini1 → cgra1 → pool` with eight tiles, each producing 32 INT32 GEMM values and eight Pool values. Every buffered IP reserves two 128-byte regions in its existing SPM; CGRA0 exposes both regions as 64 packed INT8 bytes, while CGRA1 stays raw INT32. Gemmini input/weight storage remains separate from its publication slots. Automatic jobs patch Gemmini0's input row from TileId, both Gemmini publication rows from their own Slot, and Gemmini1's native `mvin` source from the incoming producer view. CGRA's existing relocatable ReLU binds input/output to its assigned Slot and count to copied Elements. Pool binds each final output address. The root emits 1x1 Pool-output tiles; preceding stages map each to a 2x2 input region. One input-ready event starts the whole run. Manual mode uses the same kernel with fixed local addresses and runs tiles sequentially. Automatic intermediate checks locate the final tile across local slots without assuming allocation order; all 64 final outputs are checked. Slot counts and strides must fit the reserved regions; increasing slots does not enlarge SPM. Existing direct-RoCC configurations and AES attachment remain unchanged.

The projected residual demo maps `conv1` and `projection` to Gemmini0, `relu` to CGRA0, `conv2` to Gemmini1, and `add` to CGRA1. Both root stages consume preloaded input; Add waits for the matching projection and Conv2 tile and copies them into separate SPM regions. Gemmini0's four slots are shared across both jobs through the existing physical-IP allocator and round-robin arbiter. The other IPs have two slots each. Conv1/ReLU regions include Conv2's halo while dependencies retain the core tile identity. Native Conv uses the lower Gemmini SPM half; compact input and weights occupy the upper half, apart from tail publication slots. Both CGRAs have 16384 INT32 words in eight banks. CGRA0 exposes two halo slots covering up to 4096 packed INT8 elements; CGRA1 exposes raw INT32 and stores final outputs outside input slots, indexed by TileId. The input is 32×32×16 and output is 16×16×32; copy capacities accommodate up to 6×6 output tiles. Conv outputs saturate to INT8; final Add+ReLU stays INT32. Output reservation includes padding to the configured maximum tile size, including clipped tiles. The synthetic tests check every output without an intermediate DRAM writeback.

## Interface contracts

- Runtime configurations are trusted: tensor shapes, SPM regions, command counts and field updates must fit the selected hardware and agree across endpoints. Demo inputs are checked during development, without runtime configuration validators in hardware or software. Capture acknowledgements report receipt and progress, not legality. Dependency ownership, backpressure and actual DMA completion/error handling remain hardware responsibilities.
- Single- and multi-CGRA systems share the raw CPU/RoCC packet interface through `custom0`. `tests/include/cgra_runtime.h` provides packet transport and single-CGRA kernel operations without MMIO dependencies; multi-CGRA hot paths still send their preencoded packets directly.
- The system bus can read and write Gemmini's four-bank shared external SPM. CGRA's TileLink DMA master pulls from it into CGRA local SPM.
- Gemmini's ordinary DMA routes accesses to its own shared SPM locally; other addresses retain the system-bus path. The local address range comes from the existing SPM configuration, and other masters retain their system-bus access to the same memory. The existing `mvout_spad` path remains available. These direct connections retain the integrated configurations' synchronous clock contract.
- Manual `cgra_dma_mvin_i8_async` reads packed signed INT8 and expands each byte into one INT32 CGRA SPM word. `CGRA_DMA_I8_DESC_CONST` takes the element count; the encoded DMA descriptor counts destination bytes, so N source bytes occupy 4N SPM bytes. The wrapper supports unaligned source addresses and exact byte tails using sub-beat TileLink reads, and reports completion only after native DMA finishes the SPM writes. Packed input bypasses requantization; the existing raw INT32 DMA path remains unchanged. This wrapper-only command does not change VectorCGRA's native packet protocol.
- Automatic copies select packed CGRA input with `source_format: int8`. `size_bytes` counts source bytes; the generator infers four times that destination SPM occupancy and carries both lengths through AutoLink. Do not combine `source_format` with the existing `format` transformation on one dependency.
- Gemmini reports completion after the job's final command is submitted and native `busy` drains, including outstanding DMA writes. Captured automatic jobs use their declared command count. CPU-issued producers call `gemmini_commands_end()` after their final native command; this ordered `custom3/funct125` marker is consumed by the wrapper, not Gemmini. Use it inside the selected instance's `accel_commands` block on grouped systems. CPU execution commands cannot interleave an automatic job; configuration capture does not execute them. Output and compute reports retain independent handshakes. A lightweight endpoint latch retains TileLink write `denied`/`corrupt` errors until completion; it does not check addresses, byte coverage or memory type. Software owns the publication address and size contract.
- CGRA exposes one read-only TileLink SPM window at `memory.cgra_spm_window.base_address`. Its manager selects raw data or INT8 quantization at elaboration from the graph's output format; the modes do not coexist. `communication.instances.<name>.output_format: int8` also enables quantization for a terminal CGRA without an outgoing dependency. Quantized byte offset `i` reads element `outboundSpmWord + i`, while raw offsets address native SPM bytes. The YAML size describes physical SPM capacity; optional `packed_words` reserves the visible INT8 capacity, including runtime slot regions. Named instances can override this capacity with `communication.instances.<name>.packed_words`. Without a capacity setting, the window covers the declared output ranges; an explicitly quantized terminal window covers all local words from word zero. Generated `CGRA_SPM_WINDOW_SIZE_BYTES` rounds that capacity up to a cache block, with zero padding beyond the represented words. All quantized outputs share a stable mapping; there is no separate packed alias or additional data SPM. Input DMA requantization remains independent and optional, and CGRA computation stays INT32.
- Automatic Gemmini execution captures CPU-issued native RoCC commands in a parameterized wrapper buffer and replays them after `requestCompute`; it does not synthesize a fixed job or modify Gemmini.
- Gemmini captures native commands plus optional field-update descriptors before execution. Each descriptor selects an original command index, operand, bit range and `value * scale + value2 * scale2 + offset`; values come from tile geometry, a software-defined input footprint, the armed output range, slot, tile identity or outer iteration. Optional `relative` adds the original captured field, never the previous execution's patched value. Arithmetic retains 64-bit address carries before field masking; descriptors must target disjoint fields. The wrapper shares one evaluator to prepare updated fields before replay and does not decode native opcodes. A nonzero second scale takes one extra binding cycle; ordinary single-term updates retain their original latency. Zero descriptors retain ordinary native-command capture.
- Named Gemmini instances select `command_capacity` and `patch_capacity` at elaboration (defaults 16 and 32). Each job reserves these capacities; actual captured counts may differ by job. `AccelGenerated.gemminis` holds IP-owned `GemminiCacheParams`, separate from the common RoCC routing description.
- Named CGRA instances select `packet_capacity` at elaboration (default 96), exported through `AccelGenerated.cgraPackets`. This capacity bounds the captured packet array per job; full-static jobs count static packets as well as configuration and launch packets. Changing it requires regenerating and rebuilding the hardware.
- `gemmini_capture_conv` prepares one native batch-one NHWC small-tile sequence and its field descriptors. It supports full channels/kernel, no native pooling or training transforms, and fixed native A/B halves. The maximum tile must fit A/B/accumulator capacity, with publication storage separate from native working storage and input data. Changing the root partition within these constraints does not require recapture. Weights, bias, scale and activation remain CPU-configured native values. An incoming copy can supply a compact source view with global origin and valid shape covering the native read footprint, including its extra stride-minus-one extent. Copy acceptance records the view, not completed physical reads; the producer slot remains live until computation drains.
- Gemmini and CGRA configuration uses begin followed by native command or packet capture. Hardware completes capture using the declared count; Gemmini's `end()` is an optional query for capture completion, not a commit or execution barrier. CGRA's `cgra_job_config` wraps begin and packet capture without a separate end call. MMIO `CONFIG_READY`, `CONFIG_DONE`, `CONFIG_STATUS`, and `CONFIG_DETAIL` describe configuration separately from execution results. Hardware execution does not wait for the CPU to read these fields.
- CGRA templates optionally capture payload relocations before native replay packets. Software folds each symbol's base/stride and patch's scale/offset into a source, coefficient and bias, modulo 32 bits; hardware applies one affine update to Slot, TileId or Elements. Elements selects the last successful incoming copy's destination bytes divided by the CGRA word size and is latched when computation starts, so the next copy cannot change the active replay. Relocations come from kernel metadata, index the captured array and target only the generated data-payload field. Each job keeps one packet array; there is no hardware symbol cache or separate static-configuration store in the adapter.
- Generated `cgra_kernel_t` descriptors reference one static, configuration and launch packet array per kernel, expected completion counts and relocation metadata; they do not duplicate packet storage for different execution modes. Kernel YAML owns the completion count. Static packets contain native control words and static routing prologue settings. Configuration packets contain a REARM prefix, a fixed-setup prefix, then per-run initialization. `rearm_count` and `setup_count` describe the two prefix lengths. Fixed setup contains the control range, II and unpatched total step counts; constants, FU prologue and patched total counts remain per-run. Relocations index the reordered configuration array followed by launch packets. REARM preserves static control/routing configuration and SPM, clears execution state, and holds neighbor inputs under backpressure until LAUNCH. It is locally ordered before following packets without a global acknowledgement and is valid only between completed executions, not for preemption. The wrapper has no job-switch hard reset. The SoC demos do not issue native TERMINATE, PAUSE, PRESERVE or RESUME; they run resident kernels from the beginning rather than restoring interrupted execution.
- Manual `cgra_config(kernel, mode)` loads static configuration then prepares execution without launching; `cgra_prepare(kernel, mode)` reuses an already resident static configuration. `CGRA_COLD` skips REARM only for the physical CGRA's first execution after hardware reset. `CGRA_REPEAT` rearms the same kernel and skips its retained fixed setup. `CGRA_SWITCH` rearms and reloads fixed setup after another kernel or parameter set has used the CGRA. First use of a new kernel after another kernel ran is a switch, not a cold start. The caller explicitly selects the mode; there is no implicit loaded-kernel registry. `cgra_start(kernel)` sets the expected completion count and sends LAUNCH after input DMA completes. Start the most recently prepared kernel; initialization can overlap input DMA. Control-memory ranges must not overlap while kernels are resident; allocation remains software-owned.
- ResNet's CPU-controlled Softmax tail runs only after all block, Pool and FC work completes. It reuses CGRA0 scratch words 0–73 without overwriting the retained stem or CGRA1 block outputs. FC publishes INT32 logits after its working rows in Gemmini0 SPM; raw CGRA DMA transfers them with beat-aligned padding that Softmax does not read. The three phases overwrite control memory at base zero sequentially, using `CGRA_SWITCH` and waiting for completion between phases. Q15 output is read through native RoCC; the packed INT8 window is unchanged. Reload ReLU before starting another inference on the same hardware.
- Fast-API generation explicitly initializes each crossbar prologue input used by a static control word, including zero values. This prevents old nonzero prologues from surviving when a new kernel replaces that control-memory range; repeated execution does not resend static configuration.
- Automatic `cgra_job_config(id, kernel, bindings)` preloads static packets through ordinary RoCC, then captures configuration and launch packets with optional field updates and their REARM/setup prefix lengths. It drains the native CPU packet path before beginning MMIO capture. Null bindings capture the generated values without updates; otherwise the kernel's relocation metadata selects the supplied symbols. The wrapper records actual CPU or automatic launches, not capture-only packets. The adapter skips REARM before the first physical execution and skips fixed setup only when repeating its last job without recapture or intervening native configuration. Other job executions reload setup. Skipping a prefix preserves the captured packet indices and patch addresses. Configure jobs before releasing dependencies; hardware selects the execution mode for each tile without CPU intervention. AutoLink requests execution only after dependencies are satisfied, and repeated executions or tiles reuse the captured jobs. DMA and result APIs remain separate; `cgra_link_wait()` receives an AutoLink stage result, not just a CGRA completion.
- `cgra_job_full[_at](id, kernel, bindings, next_job)` instead captures REARM, static controls, fixed setup, per-run initialization and launch in the existing packet cache. It does not preload static controls. Static packets become part of the setup prefix and relocation indices shift by their count, so changing jobs restores overlapping control-memory ranges and repeating the same job can reuse setup. Its next-job encoding is zero for the last phase or the next job ID plus one. Existing `cgra_job_config` and `cgra_job_sequence` retain their resident-static behavior.
- `cgra_job_sequence[_at]` configures an ordered list of distinct cached CGRA jobs. AutoLink starts its first job; the adapter waits for every phase's native completions before preparing the next, retaining the outer tile, slot and copied element count. Only the last phase publishes output and reports the outer job complete. Each cached job stores a next-job link (zero ends the sequence; otherwise the value is the next ID plus one), without duplicating packet storage. The list and resident control ranges are software-owned. Runtime bindings may also use the stage tile's `Row` and `Rows`; scalar `columns` and `row` symbols are values, not SPM addresses. A symbol used only for total execution count does not need a dummy kernel constant.
- The deferred tiled residual test reserves separate SPM regions for each tile's skip data and final output, indexed by TileId rather than the live buffer ring. Skip data is preloaded before each run; CPU validation reads the quantized SPM window after the whole run. Changing the tile partition requires corresponding skip preloading; there is no CPU intervention between tiles.
- Graph `buffers` declare a physical or software-bound `address`, `size_bytes`, optional `format`, reusable-slot `stride` and `bytes_per_pixel`. Stage `output.buffer` and dependency `buffer` reference the same storage; a dependency may select a subrange. An explicit dependency `size_bytes` selects a fixed length instead of inheriting `bytes_per_pixel`; that subrange must be present in every produced tile, including clipped tails. Each produced buffer has one producer, and a producer has one output buffer, with any supported fan-out sharing that buffer. Root buffers are supplied before `input_ready`. These descriptions lower to the existing output and transfer registers; there is no hardware buffer table, memory allocator or DRAM stage. Software owns addresses and terminal-output lifetime. Static constant-address graphs initialize the same registers used by loaded graphs; symbolic addresses require `auto_link_load` bindings before execution.
- Automatic CGRA execution leaves results in local SPM and publishes readiness when computation completes; consumers pull from its read-only window. The CGRA adapter only requests DMA input copies and has no output DMA state machine. The generator rejects a CGRA `output.buffer`; automatic CGRA-to-DRAM writeback is unsupported. After graph drain, software can explicitly request raw output with `cgra_dma_mvout_async` or packed INT8 output with `cgra_dma_mvout_i8_async`, then wait for DMA completion. Manual packing retains its independent outbound converter with the generated output scale; raw writes bypass it. The native serial DMA receives each beat acknowledgement only after the corresponding packed writes complete, including boundary splits. This adds no second DMA engine or two-dimensional scatter.
- TileLink resolves SPM versus DRAM from the physical address; there is no memory-type flag. An explicit producer buffer also supplies the source address and slot stride to its consumers. INT8 buffer reads expand only at a CGRA destination. Root data dependencies can reference an input buffer; their source slot is zero, so generic root copies do not automatically walk a tensor by tile ID. Slot strides describe reusable regions, not final tensor placement; native IP address updates remain responsible for tiled layouts. Implicit CGRA SPM sources must match the hardware's fixed raw/INT8 window representation. Gemmini output uses a compatible captured native command and the existing `OutputAddress` patch; the wrapper does not synthesize or replace its opcode.
- AutoLink snapshots an entire run before emitting row-major tile identities with clipped tails. `communication.buffer_slots` maps physical endpoint names to slot counts (default one). SPM-backed endpoints track local regions; streaming producers track an external output-region lease. Neither adds a shared data buffer. Slot allocation is independent of tile identity and other endpoints. A slot remains occupied until its producing stage releases it and every data consumer finishes reading. CGRA/Pool release their source on actual copy completion; Gemmini releases it on compute completion because its copy only accepts metadata. CGRA input and output retain the same local slot; streaming Pool does not allocate SPM. Dependency queues preserve order and join identity. Buffered endpoints have separate copy and execution ownership; each stage retains at most one preparing input beside its active execution, without another job configuration cache. Output watches belong to execution, and the next REARM/replay waits for the previous execution to finish. Other endpoints retain single ownership. Per-stage results summarize the run at its final tile and retain the first failure. Direct data edges between stages on the same physical endpoint are rejected.
- Gemmini, CGRA and AES stages may reserve `jobs: N` cached configurations (default one); Pool retains its single RoCC-configured parameter set. Job ranges are contiguous within each graph's endpoint bindings; generated `AUTO_LINK_JOB_<STAGE>` is the base and `_COUNT` is the reserved size. `auto_link_job(stage, job)` selects a cached configuration for the staging run. Physical-IP arbitration and slot ownership identify the logical stage; endpoint requests and results carry the selected job ID. Runtime selections must fit the endpoint's generated job capacity.
- `communication.run_capacity` enables a bounded run-description cache (default zero, so legacy configurations instantiate no cache or sequencer). `auto_link_run_config(id)` captures the staging tile plan, transfers, regions, graph and selected jobs without repetition. `auto_link_run_repeat(id, first, count)` instead marks this profile as the end of an interval starting at the absolute profile index `first`, repeated `count` times in total; zero selects no repetition. `auto_link_run(first, count)` snapshots a consecutive submitted range and advances or repeats only after each run drains, stopping on an actual stage failure. Repeated intervals must be disjoint, nonnested and contained in that range. Sequential intervals share one iteration counter; it resets on launch and when an interval finishes. The iteration travels with the tile independently of its geometry and identity. The existing `auto_link_input_ready()` starts the current staging description without using the cache and uses iteration zero. Configure profiles and jobs before launch; do not overwrite active configurations. `RUNNING` covers queued runs and the entire cached sequence; fabric cycle/overlap/peak counters still describe one profile, not the sequence total.
- Completion reports remain one summary per enabled stage per run, including repeated runs. `communication.capacity.results` independently sizes the CPU result FIFO; its default retains the existing run-capacity times stage-count depth, with at least two entries. To read only after a sequence finishes, reserve space for all reports. A failed sequence may terminate early, so software drains available reports rather than waiting for the successful-case count unconditionally.
- The two-block demo uses full-width output strips so each block's packed output is contiguous NHWC, including a clipped final strip. CGRA1 reserves separate input slots, block0 output and block1 output within its 64 KiB SPM. Next-block Conv1/projection read the previous packed output through native Gemmini DMA; there is no whole-tensor pre-copy or extra stage. Output allocation and per-job addresses remain software-owned. Blocks run sequentially, and both results remain valid through final checking.
- `auto_link_transfer` configures source/destination offsets, slot strides and source bytes per pixel. Zero bytes per pixel selects the configured edge length; otherwise the source stage's mapped area determines the length, which must fit the selected hardware capacity. Buffered input regions must satisfy the DMA alignment and slot-capacity contract; direct readers do not reserve destination SPM. Software assigns nonaliasing physical regions across jobs, including aliases between packed publication windows and native SPM addresses.
- `auto_link_region` maps a root tile through row/column steps, leading halos and signed trailing adjustments, clipped to a full tensor shape. Zero full rows selects the unchanged root region. Execution requests use mapped stage regions; copies also carry their producer's region. Dependency identity is never replaced by a halo-expanded region. These descriptors and templates are configured once, not once per tile.
- Root `EMITTING` describes cursor emission; `RUNNING` remains set until all tile slots drain. `CYCLES` counts fabric run cycles, `OVERLAP` counts cycles with active task intervals on different IPs and different tile IDs, and `PEAK_ACTIVE` records the maximum number of distinct tile IDs active across IPs. Each IP contributes one tile identity, prioritizing execution when it also prepares another input; these counters do not measure same-IP DMA/compute overlap or arithmetic-unit utilization. MMIO staging writes do not change the active run snapshot.
- Root, Fabric and the CPU result endpoint share the fixed peripheral-bus clock and use synchronous handshakes/queues. Accelerator-side clock crossings retain asynchronous queues.
- MMIO configuration APIs use ordered accesses to the same endpoint and poll its acknowledgement; they do not issue a hardware fence, because Rocket fences also wait for RoCC execution. Callers still synchronize payload memory before making data ready or submitting a streaming job.
- Native AES software retains its source, key, mode, destination command order. The wrapper accepts source into its existing queue but holds its DMA handoff until key and mode have reached the streamer's registers and the writer has accepted the destination. These readiness flags are consumed on each source handoff; configure every job completely and keep execution sequential. Automatic descriptors use the same gate, and read/write completion reporting remains unchanged.
- AES uses MMIO to select a job and atomically submit its complete descriptor to the adapter cache. Cache depth follows the total jobs reserved by AES stages. Keys, modes, output addresses, and completion addresses are runtime values, not generated hardware constants. Configure jobs before releasing upstream; execution is sequential and active configurations must not be overwritten.
- `AES_SUBMIT` bit 0 commits the selected descriptor; bit 1 also requests root launch. Cache-only configuration does not start AES. The root job starts only after its output watch is armed; its descriptor must match the watched job and byte count. The destination also matches unless an explicit graph output buffer overrides it. It reports output only after output and completion writes drain.
- AES submission returns configuration acceptance status through the same MMIO status fields without an extra `end()` operation. Its complete descriptor sets ready and done together; these fields do not indicate execution completion. The root API combines configuration and launch in one call.
- Downstream AES selects cached configuration by `requestCopy.job`; source address and length come from that request. Generated `AUTO_LINK_JOB_*` constants identify per-IP jobs, distinct from global `AUTO_LINK_STAGE_*` indices.
- AES automatic jobs use an explicit graph output buffer when present; otherwise the cached descriptor supplies the output address. The completion address, key and mode always come from the descriptor. This does not add tile-dependent tensor layout or modify the cached descriptor or manual API; multi-job AES execution is not validated as an automatic tiled pipeline. CPU and hardware submissions share an issued-job count, and completion requires matching completed writes with no writes in flight.
- Downstream AES starts streaming on `requestCopy`, reports copy completion after all input is read, treats `requestCompute` as a continuation barrier, and reports compute completion after output and completion writes drain.
- Pool configuration writes one base parameter set through RoCC without begin/end commands or a multi-job command cache. Software completes configuration before starting the upstream producer; AutoLink `requestCopy` launches the streaming job. Manual configuration, start, and wait remain unchanged.
- Pool/AES downstream stages have exactly one data input and may have additional control dependencies. Their streaming adapters start on copy acceptance and cannot join multiple input copies. A streaming producer with downstream data readers retains one logical output-region lease until its writes and all consumers' reads finish; this uses existing slot ownership, not an added SPM. Streaming endpoints without configured storage reserve no slot when terminal. Streaming endpoints retain one slot because their configured destinations do not relocate by slot.
- Named Pool instances select `communication.instances.<name>.element_bits` at elaboration (8, 16 or 32; default 32). This changes the existing DMA, buffering and reducer element width, not the TileLink bus width or runtime configuration protocol. Pool-specific settings are generated as per-instance `PoolParams` in `AccelGenerated.pools`, separate from the common `AccelSpec`; unspecified settings use `PoolParams` defaults.
- Named Pool instances select `line_buffer_entries` at elaboration (default eight). Each entry holds one bus-width channel chunk. Capacity must cover the live window working set, including channel groups retained for reuse; the ResNet global 8×8×64 INT8 window uses 128 entries on a 256-bit bus.
- Pool Average accumulates signed elements, excludes padded samples from its divisor and rounds to the nearest integer with ties away from zero. Valid windows contain at least one input sample. A shared iterative divider processes output lanes after a window completes; it does not change DMA ordering or output backpressure. Max retains its existing final-chunk latency.
- Pool's destination command uses `rs1` for the output base and `rs2` for row stride in bytes. `pool_config_output_stride` writes a tile directly into a full NHWC tensor; `pool_config_output` selects tight rows with stride zero. A nonzero stride must cover one output row and be element-aligned. The writer skips row gaps without copying or buffering another tensor. AutoLink publication requires contiguous output and must not watch a gapped multi-row output.
- An explicit Pool graph output buffer supplies the automatic destination and selects tight rows. Without it, configured destination and tiled row placement remain unchanged. The adapter does not overwrite the cached RoCC configuration; manual execution continues to use that configuration.
- `pool_config_tiled(1)` enables peripheral binding from the output tile and compact producer view. CPU parameters describe the full input tensor, kernel, stride, padding, channels and final output base. The adapter derives each tile's input shape, four-sided edge padding, output address and full-tensor row stride without overwriting the base configuration. The engine latches the resulting parameter bundle directly; there is no native command replay or software-defined field-update table. Ordinary manual/non-tiled configuration remains symmetric and uses the same engine.
- `CgraLinkEndpoint` uses MMIO for AutoLink configuration and results. CGRA launch packet contents use RoCC.
- Regenerate after switching between scalar and vector layouts; packet width depends on the layout.
