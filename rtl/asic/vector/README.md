# Small GCN and ResNet ASIC kernels

Run `python3 scripts/asic/vector.py` from the repository root. It builds actual Verilator RTL, checks two distinct runtime inputs against existing Python references, and writes commands, source hashes, fixtures and measurements to `build/experiments/asic/vector/`.

`Gcn` is a dedicated sequential CSR gather/MAC engine with optional output ReLU. Its default physical capacity is 16 nodes, 256 edges and 128 channels. Load banks 0/1/2/3 contain row pointers, columns, signed Q15 edge weights and signed INT32 projected features. Loading occurs while idle; `start` captures `nodes` and `fused`. Every row must contain at least one edge, as in the existing self-loop GCN contract. Inputs, CSR topology and weights are runtime values. Arithmetic wraps at 32 bits; the tested fixture stays within the existing reference's INT32 bounds. Array contents are not reset. Output remains stable until `out_ready` accepts it; `done` pulses on the last accepted output.

`Vector` is one reusable streaming datapath for ReLU (operation 0), INT32 Add (1), and Add+ReLU (2). `start` captures a positive `length` and operation while idle. Input handshakes consume one left word, and for Add modes one right word. Output backpressure stalls the single result slot. Addition wraps at 32 bits and ReLU tests that signed result. `done` pulses on the last accepted output.

The GCN fixture is `gcn_data.graphs(0)[0]`, with `weights(0)` and the original/negated feature input. The ResNet fixture is the existing small 8×8×4 → 4×4×8 projected block with original/negated source values. Existing `block_data.conv` produces native-stage intermediates. This experiment checks and times only the post-convolution vector kernels, not Gemmini or a complete ResNet execution.

The staged GCN path materializes aggregation sums through the output interface and launches `Vector` ReLU. The fused path applies output ReLU inside `Gcn`. The streamed `GcnVector` wrapper directly connects the unchanged aggregate engine to the unchanged `Vector` ReLU through ready/valid. One accepted outer command starts both internal kernels; its report distinguishes one outer command from two internal starts. The internal link transfers 8192 bytes for the tested graph without host materialization. The staged ResNet residual path launches Add, materializes its outputs, then launches ReLU on the same `Vector`; the fused path uses Add+ReLU. First-stage ResNet ReLU is unchanged between modes. No unit is duplicated per call. The testbench instantiates alternatives for separate comparisons, not as one proposed system; do not synthesize the testbench as the architecture under evaluation.

Cycles include both the accepted start edge and final accepted output edge, summed across sequential kernel calls. They exclude fixture preload, configuration and host dispatch gaps. Preload and stream traffic count accepted 32-bit port transfers. Materialized intermediate bytes count each producer output plus its subsequent consumer input. These are interface measurements, not measured DRAM transactions. No-stall records are the primary kernel measurements; deterministic periodic output stalls check backpressure separately. The chained test withholds output readiness for 20 cycles out of 97 and verifies that backpressure reaches the internal link. Other kernel tests withhold output readiness for one cycle out of seven. The harness checks all outputs, expected counts and completion, including repeated execution without reset.

These are standalone RTL prototypes. Their cycle counts do not establish SoC performance or achieved clock frequency. The storage arrays require explicit, consistent accounting in ASIC synthesis; this source does not claim mapped SRAM macros or matched storage against a CGRA.
